# Simple Spec — простой способ разработки через ИИ-агентов
Система превращает хаотичную разработку в управляемый конвейер: `Spec` (что нужно) → `Todo` (как реализуем) → `Code` (результат).
Это попытка сделать "по-своему" Spec Driven Development. В основном упрощённый вариант.

## Определения
- **Dev Unit** — папка с `spec.md` + `todo.md` + `agent.md`. Минимальная единица работы агента. Dev Units могут вкладываться друг в друга, образуя каркас приложения.
- **Spec** — центральная сущность Dev Unit, описывающая требования, границы и цели артефакта. Описывает **поведение** ("что система делает"), а не технологии.
- **Todo** — задача на исполнение агентом.
- **UserStory** — короткая история от лица пользователя в формате «Кто / Что хочет / Зачем» (+ опционально примеры в свободной форме). Хранится в папке `user-story/` в корне приложения. **Это главный источник правды** и обязательная точка входа для любого нового поведения. Формат намеренно простой, чтобы story мог написать любой взрослый человек, а не только продакт; детали см. в `commands/user-story.md`. Технические задачи (рефакторинг, обновление зависимостей) могут заходить и без story, но идут по тому же пайплайну.

## Инвентарь
Внутри одного Dev Unit всегда есть файлы:
- `spec.md` — только требования к поведению. Может быть папкой `spec/`, если требований стало много. **Самодостаточен на своём уровне**: дочерний spec не обязан читать родительский, синхронизация идёт через процесс `/specify`, а не через файл.
- `todo.md` — локальный список задач по реализации текущего `spec.md`. Каждая задача атомарна.
- `agent.md` — описывает агента: роль, скилы, инструменты, запреты, предпочтения, какую модель использовать. Здесь же живут **технологические дефолты** ("предпочитает JWT для auth", "использует Postgres") — это предпочтения исполнителя, а не требования системы. Также содержит:
    - краткое описание Dev Unit;
    - контекст из двух частей: **«моё»** — над чем юнит работает и может менять; **«должен знать»** — только для чтения, в т.ч. ссылки на чужие контракты (например, `../backend/spec/api.md`);
    - порядок обхода дочерних dev units (например, backend заканчивает до того, как запустим frontend);
    - **правила самопроверки**: какие проверки агент гонит после задачи (тесты, линтер, демо в браузере и т.д.), сколько попыток на одну задачу, что делать при исчерпании попыток (по умолчанию — эскалация родителю с описанием попыток).
- `architecture.md` — только в корне приложения. Описывает всё дерево dev units, межсоседние зависимости и порядок обхода. Хранится отдельно для режимов `/architect` и `/specify`.

## Базовые принципы

**Всё запускается от корня.** Любое изменение spec'ов входит через корневой агент и спускается по дереву. Не вызываем агента посреди дерева напрямую. Координация и согласование контрактов — задача родителя.

**Spec самодостаточен на каждом уровне; синхронизация — через процесс, а не через файл.** Дочерний spec не читает родительский. Когда корень получает новую story, он:
1. Адаптирует свой spec, если требуется.
2. Решает, каких детей касается изменение, и спускает story (с локальными уточнениями) рекурсивно.
3. Если ребёнок видит конфликт со своим spec — возвращает его наверх, родитель решает.

При **удалении** требования у родителя `/specify` каскадно проходит по детям и удаляет связанные части. Целостность системы по файлам статически не проверяется; для этого есть `/audit`.

**Read-context vs write-context.**
- *Write-context* (где юнит может менять) — строго своё поддерево. Это и определяет дерево dev units.
- *Read-context* (откуда юнит читает) — любой источник, объявленный в `agent.md` секции «должен знать». Так frontend подписывается на API-контракт backend.

**Циклы между соседями запрещены.** Если два юнита взаимно зависят — общее знание выносится в их общего родителя.

**Минимально достаточно сейчас + явные точки расширения для известных будущих требований.** Не «делаем максимально гибко» — это путь к over-engineering. Гибкость закладывается там, где она уже понятна.

**При неопределённости агент спрашивает человека, а не угадывает.** Это сквозное правило для всех режимов: если что-то можно решить только догадкой (приоритет, выбор между двумя архитектурами, дубликат это или новая задача) — лучше задать вопрос, чем выбрать неправильно молча.

**Двухуровневый контроль качества.** Агент проверяет свою работу по правилам из своего `agent.md`. Родительский агент дополнительно проверяет результат ребёнка — но только по своему контракту с ним (например: «ребёнок сказал, что endpoint готов — родитель проверяет, что endpoint отвечает по спеке»). Внутренности ребёнка родитель не валидирует. На корне роль родителя играет человек.

## Режимы работы
- **`/architect`** — обсуждение архитектуры (дерева dev units). Формирует/уточняет `architecture.md` и `agent.md` каждого dev unit. Использует `agent.md` верхнего уровня как набор правил. На пустом проекте стартует с **шаблона нулевого `agent.md`** — это решает bootstrap.
- **`/specify`** — формирует/уточняет `spec.md`. Запускается от корня и спускается по дереву; на каждом уровне работает интерактивно (предлагает: «вынести наверх или оставить здесь?»). Каждый уровень дописывает только свои детали.
- **`/plan`** — обсуждение реализации внутри одного dev unit. Формирует/уточняет `todo.md`. Использует агента того же уровня. Отвечает за **порядок задач**: список всегда отсортирован по зависимостям, сначала задачи без зависимостей, дальше — те, что от них зависят. Новая задача вставляется не в конец, а в правильное место в очереди.
- **`/user-story`** — генерация пользовательских сценариев в `user-story/` в формате «Кто / Что хочет / Зачем». Следит за тем, чтобы в story не утекли технологии, критерии приёмки, размытые формулировки и сразу несколько желаний — это уводит к другим артефактам (см. `commands/user-story.md`). Финальным шагом предлагает перейти в `/specify` для конвертации новых историй в `spec.md` + `todo.md` по дереву.
- **`/do-it`** — выполнение задач из `todo.md`. Каждая задача начинается с чистого контекста (читает только первую задачу в `todo.md`, релевантные файлы и `agent.md`). Берёт **первую** задачу — порядок в `todo.md` уже корректный (см. `/plan`). Если в процессе обнаруживает, что не хватает чего-то (артефакт, контракт, файл) — **останавливается** с сообщением, не пропускает и не идёт к следующей. Задача удаляется из `todo.md` только после успешного прохождения самопроверок из `agent.md`. При провале остаётся в `todo.md`, агент дописывает блок «попытка N: что не получилось», чтобы следующий запуск не повторял ту же ошибку. После исчерпания попыток — эскалация родителю.
- **`/audit`** — сверка кодовой базы со spec'ом. Находит расхождения и **добавляет** в `todo.md` задачи на устранение. Перед добавлением сверяется с уже существующими задачами и **не плодит дубликаты**: если новая находка — это вариация уже стоящей задачи, она не добавляется. При сомнении («это то же самое или новое?») — спрашивает человека. Тут же ловится рассинхрон по контрактам между соседями (frontend проверяет, что его код соответствует актуальной версии backend api).
- **`/import`** — миграция существующего кода в Simple Spec. Анализирует существующие файлы и генерирует черновик `spec.md` + `todo.md`.

## Общие правила работы агента (даже если они не описаны в `agent.md`)
- Агент исполняется только внутри контекста, описанного в `agent.md`.
- Каждый агент может вызывать субагента для дочернего dev unit и обязан обработать его ответ — включая эскалацию конфликтов наверх.
- При спуске story по дереву агент решает, касается ли она ребёнка. Простое правило: если story содержит концепты/имена, фигурирующие в `spec.md` или в секции «моё» из `agent.md` ребёнка — спускаем. Если непонятно — спускаем (по умолчанию). Безусловно не спускать только при явной уверенности «не касается».
- Параллельный обход поддеревьев пока не поддерживается — всё последовательно. Параллельность добавим, когда станет очевидно, где она безопасна.

## Примеры
Они находятся в `templates/`:
- **game-v1** — самая простая реализация, из одного dev unit, итоговый результат — `index.html`.
- **game-v2** — посложнее: есть сервер, через него раздаётся `index.html` и другие ресурсы.
